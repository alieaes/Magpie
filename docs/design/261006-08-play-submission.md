# 설계: 판 기록과 점수 제출 (모든 게임 공통)

모든 게임이 같은 흐름으로 판을 시작하고 점수를 낸다. 클라이언트가 보낸 점수는 믿지 않고,
**서버가 같은 게임 로직으로 입력 기록을 다시 돌려서** 점수를 정한다 (CLAUDE.md §4-3, [랭킹 §5](./261006-06-ranking.md)).
첫 사용처는 [사과게임](./261006-09-apple-ten.md)이다.

---

## 1. 흐름

```
[시작] POST /api/plays            → 서버: 판 생성, 시드 발급, 시작 시각 기록
  ... 클라이언트가 그 시드로 플레이, 입력을 틱 번호와 함께 기록 ...
[끝]   POST /api/plays/:id/finish → 서버: 상식 검사 → 재계산 → 통과면 최고 기록 갱신
```

- **로그인 + 닉네임이 있어야** 판을 시작할 수 있다. 아니면 클라이언트가 시드를 직접 만들어 **연습 모드**로 플레이한다(기록 안 남음).
- 같은 유저가 같은 게임을 새로 시작하면, 아직 안 끝난 이전 판은 버린다(`rejected`, 사유 `abandoned`).

---

## 2. 게임이 내놓아야 하는 것 (`games/<id>/logic`)

공통 인터페이스는 `shared/src/game-logic.ts`에 둔다.

| 항목 | 내용 |
|---|---|
| `maxTicks` | 한 판 최대 틱 수 (사과게임: 120초 × 60 = 7200) |
| `maxScore` | 이론상 최고 점수 (사과게임: 170) |
| `inputSchema` | 입력 기록 형식 (Zod). 서버가 먼저 형식을 검사한다 |
| `replay(seed, inputs)` | 입력을 처음부터 다시 적용해 `{ score, ticks }`를 돌려준다. 규칙에 안 맞는 입력이 있으면 실패 |

- `replay`는 결정적이어야 한다: 시드 난수만, 고정 간격 틱(1/60초), 초월함수 없음 (CLAUDE.md §4-3).
- 클라이언트 화면(`scene`)도 같은 `logic`으로 판을 진행한다. 그래서 화면에서 본 점수와 서버가 낸 점수가 같다.

---

## 3. 시드 난수 (`shared/src/random.ts`)

- 시드는 서버가 만든 무작위 16바이트를 16진 문자열(32자)로 준다.
- 시드 문자열 → 32비트 정수 4개로 바꾸고, 그것으로 정수 난수 생성기를 돌린다. 정수 연산만 쓴다.
- 같은 시드면 브라우저·Node 어디서든 같은 수열이 나오는지 테스트로 확인한다.

---

## 4. 서버 검사 (`POST /api/plays/:id/finish`)

본문: `{ "inputs": [...], "ticks": 7200, "score": 142 }`. `score`는 클라이언트가 계산한 값으로, 비교용이다.

순서대로 검사하고, 하나라도 걸리면 `rejected`로 남기고 사유를 기록한다.

| 검사 | 걸리는 경우 | 사유 |
|---|---|---|
| 주인 | 다른 유저의 판 | (403, 기록 안 함) |
| 상태 | 이미 끝난 판 | (409, 기록 안 함) |
| 형식 | `inputSchema`에 안 맞음, 입력 개수 초과 | `bad_input` |
| 시간 | `ticks > maxTicks`, 또는 실제로 흐른 시간보다 틱이 훨씬 많음(게임 시계를 빠르게 돌림), 또는 훨씬 적음(멈추고 생각함) | `time` |
| 재계산 | `replay` 실패 | `bad_input` |
| 점수 | 재계산 점수 ≠ 클라이언트 점수, 또는 `> maxScore` | `mismatch` |

- 시간 허용 폭: 실제 경과 시간과 `ticks / 60`초의 차이가 **±5초 + 10%** 안. 네트워크 지연과 탭 전환을 감안한 값이고 튜닝한다.
- 게임 중 탭을 옮기면 브라우저가 시계를 멈출 수 있다. 사과게임처럼 제한 시간 게임은 화면이 가려지면 판을 그대로 끝낸다(§사과게임).
- 통과하면 `accepted`, 점수는 **서버가 낸 값**으로 저장한다.
- 재계산은 API 서버 안의 작업 스레드(`worker_threads`)에서 돌린다 (기술 스택 §3-3). 사과게임은 가벼워서 처음에는 바로 돌려도 되지만 같은 자리를 쓴다.

## 5. 저장

- `plays`에 열 두 개를 더한다(`005_plays_reason.sql`): `reject_reason`(위 사유), `client_score`(클라이언트가 보낸 점수, 분석용).
- 입력 기록은 JSON을 gzip으로 압축해 `play_replays`에 넣는다. 거절된 판도 남긴다(조작 분석용).
- 통과한 판은 `best_daily`(판이 끝난 시각의 KST 날짜)와 `best_alltime`을 갱신한다. 더 좋을 때만, 같은 트랜잭션에서.
- 갱신 뒤 그 게임과 총합의 랭킹 캐시를 비운다. 다른 프로세스는 10초 안에 따라온다.
- 끝나지 않고 하루가 지난 판은 하루 한 번 `rejected`(사유 `abandoned`)로 정리한다.

## 6. API

| 요청 | 본문 | 응답 |
|---|---|---|
| `POST /api/plays` | `{ "gameId": "apple-ten" }` | `{ "playId": 123, "seed": "9f3c..." }`. 비로그인 `401`, 닉네임 전 `403` |
| `POST /api/plays/:id/finish` | `{ "inputs", "ticks", "score" }` | `{ "accepted": true, "score": 142, "best": { "today": true, "allTime": false }, "rank": { "today": 3 } }` 또는 `{ "accepted": false, "reason": "time" }` |

- 요청 횟수 제한: 유저당 판 시작 분당 20회. 넘으면 `429`.

---

## 7. 막지 못하는 것

- 프로그램이 대신 완벽하게 플레이하는 봇·자동 풀이는 유효한 입력 기록을 만든다. 이건 재계산으로 못 막는다.
- 나중에: 입력 간격이 사람으로 불가능하게 짧거나 지나치게 일정한지 보는 검사, 관리자 기록 삭제. 따로 설계한다.
