# 설계: 관리자 기능

조작·부적절한 기록과 닉네임을 정리한다. [로그인 설계](./261006-07-login.md) §7에서 이어진다.

---

## 1. 누가 관리자인가

- `users`에 `role` 열을 더한다(`user` / `admin`, 기본 `user`). 스키마 `006_users_role.sql`.
  (`005`는 점수 제출 설계가 쓰기로 했다.)
- **관리자 지정은 화면에서 하지 않는다.** 서버 PC나 개발 PC에서 명령으로만 한다. 화면에 권한 주기 기능이 있으면 그 자체가 공격 대상이 되기 때문이다.

```bash
pnpm admin:grant 까치      # 닉네임으로 관리자 지정
pnpm admin:revoke 까치
pnpm admin:list
```

- `GET /api/me` 응답에 `isAdmin`을 더한다. 화면은 이 값으로 관리 메뉴를 보여준다. 실제 권한 확인은 항상 서버가 한다.

---

## 2. 관리 기능

| 기능 | 하는 일 | 어디서 |
|---|---|---|
| **기록 삭제** | 그 최고 기록을 만든 판을 거절(`rejected`, 사유 `admin`)로 바꾸고, 그 판을 가리키는 `best_daily`·`best_alltime` 줄을 지운다 | 랭킹 페이지, 게임별 탭 |
| **닉네임 초기화** | 닉네임을 비운다(`NULL`). 그 유저는 다음 접속 때 닉네임을 다시 정해야 하고, 그 전까지 랭킹에는 "이름 없음"으로 나온다 | 랭킹 페이지, 모든 탭 |

- 기록 삭제는 그 판의 기록만 빠진다. 그 유저의 두 번째로 좋은 기록이 대신 올라오지는 않는다(최고 기록 표는 1등 기록만 들고 있으므로).
- 총합 탭에는 판 하나가 없으므로(여러 게임의 합) 기록 삭제는 게임별 탭에서만 한다.
- 처리한 뒤 랭킹 캐시를 비운다.
- 닉네임을 다른 이름으로 바꿔 주는 기능은 넣지 않는다. 초기화하면 본인이 다시 정한다.

---

## 3. 작업 기록

관리자가 한 일은 모두 `admin_actions` 표에 남긴다(같은 `006` 스키마).

| 열 | 내용 |
|---|---|
| `id`, `created_at` | |
| `admin_user_id` | 처리한 관리자 |
| `action` | `remove_play` / `reset_nickname` |
| `target_user_id`, `play_id` | 대상 |
| `detail` | 처리 전 값 (예: 지운 점수, 이전 닉네임) |

- 대상 유저가 탈퇴하면 `target_user_id`는 숫자만 남는다(외래 키 없음).

---

## 4. API

모두 관리자만. 아니면 `403`. 요청 위조 방지(Origin 확인)를 받는다.

| 요청 | 하는 일 |
|---|---|
| `POST /api/admin/plays/:playId/remove` | 기록 삭제 |
| `POST /api/admin/users/:userId/reset-nickname` | 닉네임 초기화 |

- 랭킹 API는 요청한 사람이 관리자일 때만 각 줄에 `userId`와 `playId`(게임별 탭)를 더해 준다. 일반 유저에게는 지금처럼 순위·닉네임·점수만 간다.

---

## 5. 화면

- 관리자로 로그인하면 랭킹 페이지 각 줄 오른쪽에 점 세 개 버튼이 생긴다 → 메뉴 "기록 삭제"(게임별 탭만), "닉네임 초기화".
- 누르면 확인 창: "테스트03의 사과게임 142개 기록을 지울까요? 되돌릴 수 없어요."
- 메인 패널에는 관리 메뉴를 두지 않는다(실수 방지). 랭킹 페이지에서만 한다.
- 상단 아바타에 작은 "관리자" 표시를 단다.

## 6. 결정 필요

- [ ] 관리자 지정은 명령(`pnpm admin:grant`)으로만
- [ ] 기능 두 가지: 기록 삭제, 닉네임 초기화 (다른 이름으로 바꿔 주기·유저 차단은 넣지 않음)
- [ ] 관리 메뉴는 랭킹 페이지에서만
