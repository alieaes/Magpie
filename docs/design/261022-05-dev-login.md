# 설계: 개발용 테스트 로그인

개발 PC에서 돌릴 때(`run_dev.cmd`, `pnpm dev`, VS Code "Magpie: 전체") Google 로그인 없이 **테스트 계정으로 로그인**해서 저장·강화·랭킹·닉네임까지 실제 흐름 그대로 시험할 수 있게 한다.

지금은 로그인하지 않으면 체험(하루 한 번, 저장·강화 없음)만 되고, 로그인하려면 Google 설정과 계정이 있어야 한다. 붕어빵 가게처럼 여러 날 이어 가는 게임은 체험만으로는 강화·레벨업·저장 흐름을 볼 수 없다.

---

## 1. 동작

- 로그아웃 상태에서 상단 바 [로그인]을 누르면, 개발 모드일 때만 작은 **로그인 창**이 뜬다.
  - [Google로 로그인] (Google 설정이 있을 때만 켜짐)
  - [테스트1] [테스트2] [테스트3] — 누르면 바로 그 계정으로 로그인하고 지금 화면을 다시 불러온다.
- 게임 안 [로그인하고 저장] 등 다른 로그인 버튼도 같은 창을 연다(셸의 로그인 입구가 하나라서 저절로 같다).
- 테스트 계정은 보통 계정과 똑같다: 세션 쿠키, 저장, 강화, 판 제출, 랭킹, 닉네임 변경, 탈퇴, `pnpm admin:grant`로 관리자 지정까지 된다.
- 처음 로그인할 때 닉네임을 "테스트1"처럼 채워 둔다(이미 누가 쓰고 있으면 비워 두고, 그러면 보통처럼 닉네임 창이 뜬다).
- 운영(배포한 사이트)에서는 이 창도, 서버 경로도 없다(§3).

계정이 셋인 까닭: 랭킹 순위나 "다른 곳에서 가게가 바뀜(stale_save)" 같은 여러 계정·여러 창 상황을 시험할 수 있게. 늘릴 일이 있으면 숫자만 바꾼다.

---

## 2. 서버

| 요청 | 하는 일 |
|---|---|
| `POST /auth/dev-login` `{ account: 1~3 }` | 테스트 계정(`users.google_sub = 'dev-login:<번호>'`)을 찾거나 만들고 세션 쿠키를 준다. `204`. 꺼져 있으면 `404` |
| `GET /api/me` | 응답에 `devLogin: boolean`을 더한다(켜져 있는지) |

- 로그인 처리(유저 찾기·만들기, 세션 만들기, 쿠키)는 Google 로그인과 같은 함수(`findOrCreateUser`, `createSession`, `setSessionCookie`)를 쓴다.
- POST라서 지금 요청 위조 방지(Origin이 `SITE_URL`과 같아야 함)를 그대로 받는다.
- `google_sub` 앞머리 `dev-login:`은 개발 시드 유저(`dev-seed:`)와 겹치지 않는다. Google의 `sub`는 숫자만이라 실제 계정과도 겹치지 않는다.

---

## 3. 켜지는 조건 (운영에서 절대 켜지지 않게)

아래를 **모두** 만족할 때만 켠다. 하나라도 아니면 경로가 없는 것처럼 `404`, `/api/me`의 `devLogin: false`.

| 조건 | 까닭 |
|---|---|
| `DB_NAME`이 `-dev`로 끝난다 | 개발 시드(`pnpm db:seed-dev`)·랭킹 SQL 테스트와 같은 규칙. 운영 DB는 `magpie` |
| `SITE_URL`의 호스트가 `localhost` 또는 `127.0.0.1` | 운영은 `https://magpie.aviaryhub.org` |
| `.env`의 `DEV_LOGIN`이 `0`이 아니다 | 개발 중에도 끄고 싶을 때 (기본은 켬) |

- 서버가 켜질 때 한 줄 남긴다: `[auth] 개발용 테스트 로그인 켜짐 (테스트1~3)`.
- 클라이언트도 개발 빌드(`import.meta.env.DEV`)에서만 로그인 창 코드를 쓴다. 운영 빌드에서는 서버가 켜져 있다고 해도 창이 뜨지 않는다.

---

## 4. 화면

- `client/src/components/LoginDialog.vue`(새 파일): 제목 "로그인", [Google로 로그인], 구분선 아래 "개발용 테스트 계정" [테스트1] [테스트2] [테스트3], 닫기. 모바일·PC 둘 다 가운데 창.
- 셸의 로그인 입구(`auth.login()`): 개발 모드이고 `devLogin`이면 이 창을 열고, 아니면 지금처럼 Google로 보낸다.
- 테스트 계정으로 로그인하면 같은 주소로 페이지를 다시 불러온다(로그인 뒤 상태를 Google 로그인과 똑같이 만들기 위해).
- 상단 바의 [로그인] 버튼은 Google 설정이 없어도 `devLogin`이면 켠다.

## 6. 테스트

- 서버: 세 조건이 다 맞을 때만 `/auth/dev-login`이 `204` + 세션 쿠키, 하나라도 아니면 `404`(DB 이름, SITE_URL, `DEV_LOGIN=0` 각각). 같은 번호로 다시 로그인하면 같은 유저. 잘못된 번호(0, 4, 문자)는 `400`. 다른 Origin이면 `403`. `/api/me`의 `devLogin`.
- 화면: 개발 서버에서 로그인 창 → 테스트1 로그인 → 붕어빵 가게 저장·강화 → 로그아웃 → 테스트2로 다시.

## 7. 검토한 대안

| 대안 | 판단 |
|---|---|
| 클라이언트만으로 "개발용 체험" (체험에서도 강화·여러 날 허용, 저장은 브라우저에) | 서버 저장·검증·랭킹을 거치지 않아서 실제 흐름을 시험하지 못한다 |
| 개발용 Google 계정을 따로 만들어 쓰기 | Google 설정과 계정 전환이 번거롭고, 여러 계정 시험이 어렵다 |
| `GET /auth/dev?account=1` 주소로 바로 로그인 | 주소만 열어도 로그인돼서 다른 사이트가 몰래 로그인시킬 수 있다. POST + Origin 확인이 낫다 |

## 9. 구현 메모 (2026-10-22)

설계대로 만들었다. 확정 규칙은 [스펙 auth.md](../spec/auth.md) "개발용 테스트 로그인".

- 계정 수(3)는 서버(번호 검사)와 화면(버튼)이 같이 쓰므로 `shared`의 `DEV_LOGIN_ACCOUNTS`에 두었다.
- 꺼져 있을 때 `/auth/dev-login`은 본문 검사보다 먼저 `404`를 돌려준다(경로가 없는 것처럼).
- 닉네임은 계정을 **처음 만들 때만** 채운다. 나중에 닉네임을 비우거나 바꿔도 다시 덮어쓰지 않는다.
- 테스트: 켜지는 조건(DB 이름·사이트 주소·`DEV_LOGIN=0`, `localhost.evil.example` 같은 주소 거르기), 꺼졌을 때 `404`, 잘못된 번호 `400`, 다른 사이트 `403`, 개발 DB에서 세션 쿠키·같은 번호 같은 유저·닉네임 채우기·중복 닉네임이면 비우기.
- 화면 검증: 따로 띄운 개발 서버(3491/5491)에서 로그인 창 → 테스트1 로그인(닉네임 "테스트1", 붕어빵 가게가 체험이 아니라 저장 모드로 열림, 저장 API 응답) → 로그아웃 → 테스트2 로그인, 휴대폰 폭(375px)에서 창 모양을 확인했다. 개발 DB에 `dev-login:1`, `dev-login:2` 유저가 생겼다.
