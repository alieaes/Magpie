# 설계: 랭킹

게임별 랭킹과 총합 랭킹을 일간·역대로 나눠 보여준다. 기본 표기는 **일간**이다.
이 문서는 랭킹 규칙, 저장 방식, 조회 API를 정한다. 화면은 [메인 페이지 설계](./261006-05-main-page.md)에서 다룬다.

---

## 1. 랭킹 종류

| | 일간 (기본) | 역대 최고 |
|---|---|---|
| **게임별** | 오늘 그 게임 최고 기록 순 | 전체 기간 그 게임 최고 기록 순 |
| **총합** | 오늘 게임별 환산점 합 순 | 역대 게임별 환산점 합 순 |

---

## 2. 기간

- **일간**: 한국 시간(KST, UTC+9) 00:00부터 다음 날 00:00까지. 매일 00:00에 새로 시작한다.
  기록 시각은 UTC로 저장하고, "어느 날 기록인지"는 KST 날짜로 계산한다.
- **역대**: 서비스 시작부터 지금까지.
- 지난 날의 일간 랭킹(어제 1위 등)은 데이터가 남으므로 나중에 볼 수 있다. 이번 범위에는 넣지 않는다.

---

## 3. 게임별 랭킹

- 유저당 한 줄. 그 기간의 **최고 기록 하나**만 올라간다.
- 정렬은 게임 목록의 `sort`를 따른다. 대부분 높을수록 좋음(`desc`)이고, 1to50 같은 기록 게임은 낮을수록 좋음(`asc`)이다.
- 동점이면 **먼저 달성한 사람이 위**다. 그래서 순위가 겹치지 않는다(1, 2, 3, ...).

---

## 4. 총합 랭킹 — 정규화

게임마다 점수 크기가 아주 다르다(사과 0~170, 수박은 수천). 점수를 그대로 더할 수 없으므로 **순위를 점수로 바꿔서** 더한다.

### 4-1. 환산 공식

```
환산점 = round(1000 × (N − 순위 + 1) / N)
  N = 그 기간에 그 게임을 한 사람 수
```

- 1위는 항상 1000점이다. 꼴찌는 1000 / N점이다.
- 예: 4명이 했으면 1위 1000, 2위 750, 3위 500, 4위 250.
- **총합 = 그 기간에 한 게임들의 환산점 합.** 안 한 게임은 0점이다. 그래서 여러 게임을 할수록 총합이 커진다.
- 일간 총합은 오늘의 게임별 일간 순위로, 역대 총합은 게임별 역대 순위로 계산한다.
- 총합이 같으면, 총합에 들어간 기록 중 가장 늦은 기록을 **먼저 달성한 사람이 위**다.

### 4-2. 왜 순위 기반인가

| 방식 | 문제 |
|---|---|
| **순위 기반 (채택)** | 참여자가 적은 게임은 환산점이 크게 출렁인다(2명이면 2위가 500점) |
| 1위 대비 비율 (`내 점수 / 1위 점수 × 1000`) | 1위 한 명이 비정상적으로 높으면 나머지 모두의 환산점이 같이 깎인다. 낮을수록 좋은 게임에는 따로 공식이 필요하다 |
| 백분위 (상위 몇 %) | 순위 기반과 거의 같지만, 설명이 더 어렵다 |
| 게임마다 기준점 (`점수 / 기준점 × 1000`) | 기준점을 게임마다 정하고 계속 손봐야 한다 |

순위 기반은 점수 크기와 정렬 방향(높을수록/낮을수록)에 상관없이 같은 공식으로 처리된다.
"게임마다 1위가 1000점, 순위가 내려갈수록 깎인다"로 설명도 쉽다. 참여자가 적을 때의 출렁임은 서비스 초반에는 감수한다.

---

## 5. 어떤 기록이 랭킹에 들어가는가

**검증을 통과한 기록만** 랭킹에 들어간다. 클라이언트가 보낸 점수는 그대로 믿지 않는다.

| 단계 | 내용 | 대상 |
|---|---|---|
| 1. 상식 검사 | 점수 범위, 최소 플레이 시간, 요청 횟수 제한 | 모든 게임 |
| 2. 재계산 | 서버가 준 시드 + 입력 기록을 서버가 다시 돌려 점수를 낸다. 실제 흐른 시간과 틱 수도 비교한다 | 모든 게임 (CLAUDE.md §4-3) |

점수 제출 흐름(시드 발급, 입력 기록 형식)은 사과게임 설계에서 정하고, 다른 게임도 같은 흐름을 쓴다.
봇·자동 풀이는 재계산으로 못 막는다. 입력 간격 검사와 관리자 기록 삭제는 나중에 따로 설계한다.

## 6. 저장

### 6-1. 표

| 표 | 한 줄의 의미 | 주요 열 |
|---|---|---|
| `plays` | 한 판 | `id`, `user_id`, `game_id`, `seed`, `score`, `started_at`, `ended_at`, `status`(대기/통과/거부) |
| `play_replays` | 한 판의 입력 기록 | `play_id`, `data`(압축한 입력 기록) |
| `best_daily` | 유저 × 게임 × 날짜(KST)의 최고 기록 | `user_id`, `game_id`, `day`, `score`, `achieved_at`, `play_id` |
| `best_alltime` | 유저 × 게임의 역대 최고 기록 | `user_id`, `game_id`, `score`, `achieved_at`, `play_id` |

- 판이 검증을 통과하면 `best_daily`와 `best_alltime`을 갱신한다. 더 좋은 기록일 때만 바꾼다.
- 랭킹 조회는 `best_daily`, `best_alltime` 두 표만 본다. `plays`는 기록 보관과 재검증용이다.
- 입력 기록을 따로 두는 이유: 나중에 "상위 랭커 플레이 다시 보기"에 쓸 수 있고, 판 목록 조회를 가볍게 하기 위해서다.
- 닉네임은 `users` 표에서 붙인다. `users`는 로그인 설계가 주인이지만 랭킹을 먼저 만들므로,
  최소 열(`id`, `google_sub`, `nickname`, `created_at`)로 `001_users.sql`을 먼저 만들고 로그인 설계에서 보탠다.

### 6-2. 계산

- 게임별: `best_*`에서 정렬하고 `ROW_NUMBER()`로 순위를 매긴다.
- 총합: 게임별 순위와 참여자 수(`COUNT(*) OVER (PARTITION BY game_id)`)로 환산점을 낸 뒤 유저별로 더한다.
  MariaDB 10.6의 윈도우 함수로 쿼리 하나에 계산한다.
- 조회 결과는 API 프로세스 메모리에 10초 캐시한다. 랭킹은 10초 늦게 바뀌어도 괜찮다.
- 참여자가 수만 명이 되어 쿼리가 무거워지면, 그때 환산점을 미리 계산해 두는 표를 만든다.

## 7. API

### 7-1. `GET /api/rankings`

| 파라미터 | 값 | 기본값 |
|---|---|---|
| `target` | `total` 또는 게임 id | `total` |
| `period` | `daily` 또는 `alltime` | `daily` |
| `limit` | 1~100 | 10 |

응답:

```json
{
  "target": "total",
  "period": "daily",
  "day": "2026-10-06",
  "resetsAt": "2026-10-06T15:00:00Z",
  "participants": 42,
  "entries": [
    { "rank": 1, "nickname": "까치", "score": 2750 }
  ],
  "me": { "rank": 17, "score": 1320 }
}
```

- `day`, `resetsAt`은 일간일 때만 있다. `resetsAt`은 다음 KST 00:00이다.
- `me`는 로그인했고 기록이 있을 때만 있다. 순위권 밖이어도 내 순위를 준다.
- 게임별일 때 `score`는 원래 점수, 총합일 때는 환산점 합이다.

### 7-2. `GET /api/games/summary`

로비 카드에 표시할 게임별 요약.

```json
[
  {
    "gameId": "apple-ten",
    "todayTop": { "nickname": "까치", "score": 142 },
    "myTodayBest": 98,
    "myAllTimeBest": 131
  }
]
```

- `todayTop`은 오늘 기록이 없으면 `null`. `my*`는 로그인하지 않았거나 기록이 없으면 `null`.
